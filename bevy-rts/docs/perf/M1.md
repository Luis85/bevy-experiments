# M1 perf baseline

## Machine and method

Machine: Intel Core Ultra 9 185H (16 cores, 22 threads), 63.5 GB RAM, NVIDIA RTX 1000 Ada Generation Laptop GPU
(Vulkan, driver 596.71), Windows 11 Pro 10.0.26300, on mains power. rustc 1.99.1 (58cf8f9c3 2026-10-13). Sim code
at `3d78b45` (`m1/phase-a` with every M1 task merged; the Task 21 commits change no sim code), 2026-10-25.
Power plan: Balanced (`381b4222-f694-41f0-9685-ff5bb260df2e`), not switched to a fixed plan: that is a system
setting the agent may not change (R128 asks for a fixed plan; the user can rerun on one).

**Idle machine for the sim bench.** Before the run no `cargo`/`rustc` process was alive and the CPU load was
0–18 %. During the sim bench (05:29–05:32 UTC) a sampler every 3 s saw CPU load 0–39 % (median 9 %) and no
`cargo`/`rustc` process: one bench thread on a 22-thread machine. The render stress runs and the scenario timings
below were taken later, partly while another project's cargo builds kept the CPU at 100 % (said per row).

Method (R128):
1. **M0 vs M1 on the same machine, interleaved.** The `m0` tag (`0ae615d`) was checked out in a separate worktree
   (`C:/fl/m0bench`, its own build dir) and its `fl_cli` built in release. Five rounds alternated the M0 binary
   (`bench`, the open map: M0's only map) and the M1 binary (`bench --flat`, the same open-map workload), each
   `--units 500,3000,5000 --ticks 400 --warmup 40 --repeat 1 --profile`; the table takes the median of the five
   rounds per size. The worktree and its build dir were removed afterwards.
2. **M1 on terrain** (the G7 workload, `docs/perf/M1.json`): `cargo run -p fl_cli --release -- bench --units
   500,3000,5000 --ticks 400 --warmup 40 --repeat 5 --profile --out <scratch>/M1-terrain.md --json-out
   docs/perf/M1.json.new` (the same binary, written to scratch first and copied).
3. **M1 flat, repeat 5**: the same with `--flat`, written to scratch only (never into `M1.json`: the gate's
   `perf-file` row reads its 3,000-unit row, which must be the terrain run).

|---:|---:|---:|---:|---:|

Medians of five interleaved rounds; the spread of the five means was small (M0 3,000: 2.766–2.924 ms; M1
3,000: 4.385–4.607 ms; M1 5,000: 9.253–10.545 ms). `M0.json` was taken under 96–100 % foreign build load, so it
overstates M0's cost: against it, `bench --flat --baseline docs/perf/M0.json` passes (exit 0, within 20 % at
every size), but against the M0 binary on the same idle machine M1's open-map tick is **55–63 % slower**. That
is over the 20 % the brief allows, so here is where the time goes.

terrain 3000: `scale::scale_sense` 1.461, `steer::compute_steering` 1.097, `movement::move_system` 1.024, `scale::follow_system` 0.257, `spatial::track_spatial` 0.198, `path::process_path_queue` 0.105, `publish::publish_snapshot` 0.090, `spawn::spawn_funnel` 0.050

terrain 5000: `scale::scale_sense` 3.689, `steer::compute_steering` 2.747, `movement::move_system` 1.921, `scale::follow_system` 0.486, `spatial::track_spatial` 0.358, `publish::publish_snapshot` 0.164, `path::process_path_queue` 0.151, `spawn::spawn_funnel` 0.085

**Justification.** The whole 5,000-unit delta (+3.87 ms of profiler tick time) is new M1 work, not a regression
of M0 code:
- `fl_sim::steer::compute_steering` (Task 11, separation steering, phase `Think`) is **+2.56 ms**, two thirds of
  the delta. It examines `steer.pairs` ≈ 50,600 neighbour candidates per tick for 5,000 units (20,500 at 3,000).
  M0 had no steering.
- `fl_sim::movement::move_system` grows by **+1.04 ms** (0.81 → 1.84 ms): path and flow following, the terrain
  speed lookup, line-of-sight look-ahead and swept-cell checks (`move.los_cells` ≈ 10,000 per tick) and the
  slide fallbacks (R114).
- Orders and the path queue (`advance_orders`, `process_path_queue`) add 0.07 ms; every other system, M0's
  `scale_sense` (`Perceive`) included, is within 0.1 ms of M0.
The per-system rows are medians taken per system, so they need not add up to the median tick: they sum to
+3.83 ms against the tick's +3.87 ms. The cost grows superlinearly with the unit count (500 / 3,000 / 5,000
units: +0.17 / +1.64 / +3.73 ms, about +0.34 / +0.55 / +0.75 ms per 1,000 units), tracking `steer.pairs`
(about 1,400 / 21,500 / 52,900 per tick in the counter table above; the open-map run's 20,500 and 50,600 are
alike): denser crowds give each unit more neighbour candidates. Making steering
cheaper (fewer candidates per unit, idle units steered every `idle_every` ticks already) is tuning work for C7's
crowd behaviour, not a fix for M1; the budgets that gate it are the work counters (`steer.pairs`,
`move.los_cells`) in `docs/perf/budgets.ron`.

## Scenarios (Task 13, Task 10b)

The pathing scenarios are counter scenarios (`fl_test_utils/tests/perf_counters.rs`, budgets in
`docs/perf/budgets.ron`); their work counters, not wall time, are gated. Wall time from one release run
(`cargo nextest run --release -p fl_test_utils -E 'binary(perf_counters)' --test-threads 1`), **taken while another
project's cargo builds kept the CPU at 60–100 %**: each test builds its sim, runs 40 warmup and 200 measured
ticks and counts allocations, so duration / 240 is an upper bound per tick.

| Scenario | What it is | Test wall time | ≤ ms/tick | Counters over the 200 measured ticks (the blessed snapshot) |
|---|---|---:|---:|---|
| `group_move` | the 300-unit scale mix on the 2 km map without followers, projectiles or wandering; every player orders all its units to a new quadrant every 50 ticks, 5 rounds | 1.508 s | 6.3 | `flowfield.abstract_nodes` 202,656, `flowfield.cells` 442,752, `path.budget_spent` 202,656, `path.requests` 48 |
| `choke_crowd` | 192 tanks pushed through a two-cell gap (R117) | 0.921 s | 3.8 | `steer.pairs` 2,252,037, `path.budget_spent` 16,478, `path.nodes_expanded` 14,475 |
| `flow_thrash` | 36 live flow fields (over `flow_cache_max` 32), 216 riflemen | 0.644 s | 2.7 | `flowfield.abstract_nodes` 9,072 (all in the request tick: 0 per tick afterwards since Task 10b, R124; 4,571,532 before) |
| `scale_3000` / `flat_3000` | the bench mix at 3,000 units, terrain / open map | 3.027 s / 3.116 s | 12.6 / 13.0 | as `docs/perf/budgets.ron` |
| `scale_5000` (`milestone_counters_scale_5000`) | the bench mix at 5,000 units on terrain | 4.618 s | 19.2 | as `docs/perf/budgets.ron` |
| `queue_burst_drains_at_5000` | the start-up path-request burst at 5,000 units drains (R126) | 2.501 s | – | passes: the queue is empty by tick 52 |
| `path_budget_holds_at_scale` | at 3,000 units, each tick's work before its last request stays under `Path.budget_per_tick` | 1.437 s | – | passes |

The flow-cache thrash Task 13 measured (≈ 91 integrations and tiles rebuilt per tick with 36 keys; ≈ 350 ms per
tick with 60 keys on the 2 km map) is gone: with tick-boundary eviction the 36 fields are built once.
**G7** (≤ 15 ms mean per tick at 3,000 units) holds on terrain with pathing (4.613 ms, above) and in every
scenario; `scale_3000`'s 12.6 ms is a per-test upper bound with setup and allocation counting under load, not
a tick mean.

## Render stress

`cargo run -p fl_game --release -- --stress 3000 --exit-after 25 --agent` (the scale mix scaled to 3,000
wandering units on the 2 km terrain map with its terrain mesh, vsync off, a visible 1280×720 logical /
2560×1440 physical window; the first 3 s do not count). Built from `3d78b45`. Four runs at 05:51–05:53 UTC,
with none of my builds running and before the foreign builds started (CPU load not sampled):

```
stress: units=3000 avg_fps=88.0 p1_low_fps=2.6 frames=1955
stress: units=3000 avg_fps=70.6 p1_low_fps=2.1 frames=1554
stress: units=3000 avg_fps=71.1 p1_low_fps=2.1 frames=1595
stress: units=3000 avg_fps=74.1 p1_low_fps=2.1 frames=1660      (RUST_LOG=warn)
```

**avg_fps ≥ 60 holds** (median 72.6, best 88.0). M0 measured 98.8 median on the open map without a terrain
mesh. The 1 % lows are about 2 fps in every run: a few frames of roughly 0.5 s. They are not an M1 regression:
the `m0`-tag game, run interleaved with the M1 game on the same machine later (under the foreign build load,
so with lower averages), shows the same 1 % lows:

```
m0:  stress: units=3000 avg_fps=48.0 p1_low_fps=2.1 frames=1068
M1:  stress: units=3000 avg_fps=38.9 p1_low_fps=2.2 frames=857
m0:  stress: units=3000 avg_fps=33.2 p1_low_fps=2.2 frames=736
M1:  stress: units=3000 avg_fps=23.7 p1_low_fps=2.1 frames=522
```

A third interleaved pair, with no cargo build running but other processes keeping the CPU at 30–55 %:

```
m0:  stress: units=3000 avg_fps=58.5 p1_low_fps=2.0 frames=1291
M1:  stress: units=3000 avg_fps=59.9 p1_low_fps=2.1 frames=1345
m0:  stress: units=3000 avg_fps=60.3 p1_low_fps=2.1 frames=1333
M1:  stress: units=3000 avg_fps=61.2 p1_low_fps=2.2 frames=1347
```

In that one pair, run under 30–55 % background CPU with both builds near the 60 fps limit, the terrain mesh cost
nothing measurable; under heavy build load the first pair favoured M0, the second is level, so that gap was
noise. M0's own `docs/perf/M0.md` runs had 1 % lows of 7–86 fps, so the ≈ 2 fps lows look like a property of this machine today (laptop GPU, Balanced plan, the
background load) rather than of either build; finding them needs a frame profile (`--features trace_tracy`),
which this task did not take. A fully idle M0/M1 stress pair is still owed.
