## Sim bench

Machine: Intel Core Ultra 9 185H (16 cores, 22 threads), 63.5 GB RAM, NVIDIA RTX 1000 Ada Generation Laptop GPU
(Vulkan, driver 596.71), Windows 11 Pro 10.0.26200. rustc 1.99.1 (58cf8f9c3 2026-10-13). Sim code at `3500b33`
(`m0/phase-a`, Task 30), 2026-10-24. Power plan: Balanced (`381b4222-…`), not switched to a fixed plan (a
system setting the agent may not change; the user can rerun on a fixed plan).

**Not an idle machine.** Other projects' cargo builds kept the CPU at 96–100 % load through every measurement
here (between 7 and 31 foreign `cargo`/`rustc` processes). The numbers are therefore pessimistic and noisy; a
second bench run a few minutes later gave 0.570 / 4.383 / 9.400 ms mean at 500 / 3,000 / 5,000 units (within
6 % of the table).

### Reading the bench

- **G7 met:** 3,000 units (10,000 sim entities with the entity mix: followers and projectiles in flight) take
  **4.43 ms** mean per tick, p95 7.96 ms, against the 15 ms budget. 5,000 units (16,680 entities) take 9.34 ms.
- Entity counts are as the plan expects: about 1.7k, 10k and 17k.
- `Perceive` dominates and grows faster than linearly (0.15 → 2.38 → 6.09 ms): it is the spatial grid's
  relocations and queries, whose candidate count grows with density (`spatial.query_candidates` 2.3k → 76.5k
  → 210.8k per tick for 50 → 300 → 500 queries). `Act` (movement and followers) is linear. This is the first
  place to look when the sim grows (M3 vision).
- The work-counter budgets in `docs/perf/budgets.ron` are unchanged (the gate's `perf_counters` tests pass).

## Render stress

`cargo run -p fl_game --release -- --stress 3000 --exit-after 25 --agent` (the scale mix scaled to 3,000
wandering units, 10,751 client entities, vsync off, a visible 1280×720 logical / 2560×1440 physical window; the
first 3 s are not counted). Seven runs under the same foreign build load:

```
stress: units=3000 avg_fps=101.0 p1_low_fps=57.7 frames=2224
stress: units=3000 avg_fps=56.8 p1_low_fps=12.7 frames=1251
stress: units=3000 avg_fps=104.0 p1_low_fps=73.2 frames=2288
stress: units=3000 avg_fps=98.8 p1_low_fps=45.5 frames=2173
stress: units=3000 avg_fps=67.1 p1_low_fps=21.5 frames=1479
stress: units=3000 avg_fps=43.0 p1_low_fps=7.0 frames=947      (RUST_LOG=warn)
stress: units=3000 avg_fps=102.7 p1_low_fps=85.7 frames=2261   (RUST_LOG=warn)
```

**Median 98.8 fps average (best 104.0), target ≥ 60: met in five of seven runs.** The two runs below 60 and the
low 1 % lows coincide with the heaviest foreign build load (the frame rate halves when another workspace links
Bevy); they are not reproducible from one run to the next with the same binary, which points at CPU
starvation rather than the renderer. An idle-machine rerun is still owed (see the Task 30 report).

What the frame costs (dev build with `debug_remote`, `fl.perf` after 25 s of `--stress 3000`): 95 fps,
10.5 ms frames; 3,000 unit visuals but only 175–190 visible meshes after frustum culling at the stock zoom;
client feature systems (`client.view` interpolation 0.48 ms, `client.debug` 0.52 ms, placeholders 0.01 ms) are
small; the rest is Bevy's render extraction and submission. Meshes and materials are already shared per unit
type and owner (`placeholders_share_handles`), and snapshot records are rebuilt only for entities that changed (here every wandering unit, `publish.rebuilt` 3,000 per tick). No rendering
change was made: nothing measured points at the renderer, and the cheap fixes (merging placeholder parts,
turning off unit shadow casting) would change the look without a measurement that justifies them.

### Finding: debug logging of spawns costs ~30 ms per sim tick in the game

In the same dev-build stress run with the default `debug.ron` (`log_filter: "info,fl_sim=debug"`), the sim
tick took **38.0 ms** mean, of which `Lifecycle` 29.7 ms: `fl_sim::spawn` logs every spawn at DEBUG (50
projectile spawns per tick at 3,000 units), and each record goes to stderr and `log.jsonl` (~0.6 ms each).
With `RUST_LOG=info` the same run gives a 10.5 ms tick and a 0.56 ms `Lifecycle`. The headless bench is not
affected (it logs at `error`). Release builds still print the records to stderr.

Resolved in the M0 final fix wave: the default `debug.ron` filter is now
`info,fl_sim=debug,fl_sim::spawn=info`. Re-measured the same way (dev build with `debug_remote`,
`fl.perf` after 421 ticks of `--stress 3000`, machine not idle): tick mean **13.1 ms**, `Lifecycle` mean
**0.78 ms** (was 38.0 and 29.7 ms).
