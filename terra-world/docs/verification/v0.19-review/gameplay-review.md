# Gameplay, economy and progression review — 0.19 candidate

Baseline: attached Terra World 0.18.0, reviewed 29 October 2026. This is a source and documentation review; no new native play session or physical-device qualification is claimed.

## Product and code studied

Read the current gap register and implementation plan, playtest guidance and Motor Town parity priorities. Inspected the settlement/economy command and maintenance paths, transport transaction preparation, rental escrow/refunds, private depot trade/transfers, company registration/funding/household circulation, faction membership/leadership/property transfers, owner dormancy and returning-player commitments. Existing 0.18 full-state payment regressions and settlement lifecycle/conservation tests remain useful evidence, but their historical execution does not certify this increment.

## Prioritized findings

| Priority / area | Finding and concrete evidence | Proposed action / acceptance |
|---|---|---|
| P2 — suspended gameplay authority | `SandboxState::apply_settlement` is a public player-action entry point (`src/settlement/commands.rs:158`) and checks account presence but never checks `is_player_dormant`. `SandboxState::apply` blocks dormant owners (`src/commands.rs:124`), so direct SDK callers get different behavior. A disconnected owner can directly found/fund a settlement, accept/cancel/fulfill funded supply work or contribute materials while its session is suspended. | Add the same dormant-principal rejection at the public settlement entry before dispatch. Exercise both direct and wrapped calls for founding, contribution, funding, upgrade and contract acceptance/cancellation/fulfillment; compare complete state on rejection and prove the same actions are admitted after explicit resume where prerequisites permit. This closes one G03/G18 lifecycle boundary, not an observed network exploit: ordinary network commands already use the guarded wrapper. |
| P2 — controlled-motion lifecycle invariant | Public `set_controlled_motion` (`src/living/commands.rs:15`) currently writes a nonzero velocity for a dormant owner; `validate_owner_dormancy` rejects exactly that state (`src/dormancy.rs:174`). The host callers normally exclude dormant sessions, but the SDK boundary itself can violate its own durable invariant. | Add a dormant-owner rejection before motion mutation, while retaining the separate trusted administrative positioning API. Regress a rejected moving and stationary reposition, unchanged entire state, valid dormant state, then successful controlled motion after explicit resume. Root should include only if the intended SDK contract agrees that controlled motion belongs to active sessions. |
| P1 — sustainable career acceptance remains open | Current docs correctly distinguish finite conservation fixtures from a profitable beginner/advanced career. Household circulation is finite earned money, rental bonds are not spendable income, and source/vehicle/input costs must remain explicit. This review found no basis for relabeling G03 complete. | Retain G03. Next dedicated balancing work should run first/returning supply, owner-driver and depot-company strategies through scarcity, lease expiry, living costs, loaded recovery and save/reconnect, reporting startup capital, recurring cash, fuel, wages, reserved reward/bond and manual interventions separately. |
| P2 — community end-of-life policy remains open | Explicit handover/departure/removal preserve communal funds/property and revoke home access. `leave_faction` correctly rejects the sole/current leader. There is no unavailable-leader succession or dissolution policy. | Retain G06. Define who can initiate succession, timing/evidence, treasury beneficiaries and property retention before adding commands; do not invent confiscation or silent transfers as polish. |
| P2 — specialist career depth remains open | The parity document explicitly leaves individual boarding/loading, actual tow/emergency interactions, ranked events and physical trailer dynamics partial. Labels and generic deliveries do not satisfy those experiences. | Keep these as product increments with discoverable start, equipment, meaningful action, failure/recovery, durable authoritative completion and native playtest acceptance. |
| P2 — player comprehension needs observation | Commitments expose owned work, deadlines, gross reward and separate rental bonds/company cash, but source inspection cannot establish that new players understand costs or recover from a stalled trip. | Preserve G04 and the uncoached playtest protocol. Record stalls, misunderstood totals, abandoned goals and successful return journeys. Avoid adding another quest/accounting ledger. |

## Proposed bounded implementation dispatch

1. Gameplay owner: close the two active-session SDK boundaries with early mutation-free guards, document their contract and add full-state lifecycle regressions.
2. Integrator: run focused settlement and living suites, then broader sandbox/network compatibility checks to ensure resumed and ordinary authoritative paths retain behavior.
3. Independent reviewer: inspect guard placement and ensure trusted hydration/administrative positioning remains separate; check no save, wire, price, progression or ownership-policy changes were introduced.

No new command, schema, price, balance policy or authority partition is needed. Public-operation regressions are materially useful: they exercise lifecycle invariants rather than duplicate the guard implementation. Root owns all compilation because the shared target is space constrained.
