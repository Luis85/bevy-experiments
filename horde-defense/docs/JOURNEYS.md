# Incremental journey and progression contract

This document describes the current source protocol. Exact build, native interaction, balance and performance evidence belongs in [VALIDATION.md](VALIDATION.md); source presence alone is not a playthrough claim.

## Start, resume and protect an existing profile

The main menu offers New game for a fresh profile and Resume journey for an existing one. An existing journey's New game action opens a confirmation modal. Keep current journey cancels without a reset.

`runner::begin_new_journey` queues the serialized storage barrier in runner/persistence.rs: preserve unreadable source copies, archive the complete current Game under the profile's `journey-archives/journey-<stamp>-<counter>/campaign.json` when a previous profile exists, then save the fresh generation. The live Game changes only after fresh save success. Archive or save failure remains visible and leaves the current journey active; an already-created archive is retained. Display/audio/control preferences stay outside this reset, and selected difficulty is copied to the fresh campaign. No widget performs filesystem replacement. One worker receives immutable snapshots; the main thread owns tickets, epochs and navigation acknowledgments.

The fresh route is survivor confirmation → infected starting country → a Personal defense that waits for Begin defense, with the first-defense hint and the key legend on the field. Rook and June retain equal initial combat statistics; Mara is the independent NPC companion. Resume returns to an active field when one exists, to Results for an active journey with a settled round, to Camp home for a started journey without one, or to the incomplete survivor/map choice. A restored active field is paused until explicitly resumed.

## Loop map

Every screen has at most one amber primary, drawn through `ui::primary` (or its bar and modal forms), and one Escape target decided by the pure `ui::escape::escape_action`. The table is the as-built loop (production-pass plan §3.2, design-ux-flow §1 with its integration rulings).

| Screen | Amber primary | Escape |
|---|---|---|
| Main menu | Resume journey, or New game on a fresh profile | Quit confirmation: "Save and quit" (amber) or "Stay" |
| Survivor selection | Continue as <name> | Main menu |
| World map before the first start | Start journey (`ChooseStart`; the first defense opens paused) | Main menu |
| Camp home (the default camp tab) | `home_primary`: Return to active defense, Choose next country, Go to briefing or Choose a country | Results when a settled report exists, the journey is active and no defense is live; otherwise the return-to-menu confirmation |
| Briefing | Deploy personally, or Deploy <name> (`BeginDefense` for `Game::next_defender`) | Camp home |
| Equipment, Character, World map; the Mara and Operations drill-downs | Go to briefing (Choose next country after a liberation, Choose a country without an active one); World: Plan defense or Manage country (`SelectCountry`, never deploying) | Camp home; an open observer window or armory sale confirmation closes first |
| Battle | Begin defense or Resume defense, amber only while paused | Cancels a retreat hold, else closes construction, else passes to the Pause binding only when Pause is bound to Escape (the default; decision 18); otherwise ignored |
| Results | `results_primary`: Upgrade after a defeat or withdrawal whose recommended node can be bought now, else the continuation (Try again, Next defense, Choose next country or Return to active defense); the bar holds exactly Upgrade, the continuation and Leave journey | Return-to-menu confirmation: "Save and return to main menu" (amber) or "Stay" |
| Upgrades | Back to battle, Choose next country or Return to active defense; Back to camp when there is nothing to continue | Results when a round has settled, else Camp home |
| History | none | The screen it was opened from |
| Settings | Save and return to <the screen it was opened from> | Cancels a rebind prompt; else the unapplied-draft warning while the difficulty draft is not applied; else saves and returns |
| Recruit modal | Recruit as <Archetype> · <core price>, then Back to camp once the recruit joined | Closes it |

Over any screen the topmost overlay answers Escape first, in this order: a rebind prompt (cancelled), a focused text field (left to egui), an application modal (closed; the draft warning keeps editing), the new-journey confirmation (closed, unless the reset is under way), the operation details window, an open popup or menu (left to egui), the Operations observer window and an armory sale confirmation (each closed). While a save, a reset or another durable transition is pending, Escape navigates nowhere. Nothing but the router reads the Escape key (`escape_is_read_only_by_the_router`); `matrix_table` pins every row above, and `full_loop_new_game_to_recruit_defends` walks new game → Rook → country → defeat → Results → Upgrade → buy → Back to battle → victory → Next defense → liberation → Recruit → Back to camp → the recruit defends at 1440x900 and at 1050x700 with 135% scale, asserting the screen, the tab and exactly one primary at each step.

## Every main round ends on Results

Results is the debrief after a main victory, defeat or withdrawal. Its outcome strip reports already-banked coins/items; it does not award them again. It shares the camp header (History and Save are there) but has no navigation row. One bottom action bar holds exactly three buttons in fixed positions: Upgrade, the continuation (Try again, Next defense, Choose next country, or Return to active defense) and a quiet Leave journey, disabled while a save or reset is pending. The amber primary is Upgrade after a defeat or withdrawal whose recommended node can be bought now, otherwise the continuation. Under the outcome line, a loss shows the core `Report.cause` and `Report.tip` wrapped in full ("Overrun at the line in lane 2. Aim at the nearest runner first…"); a victory names what it opened: the fronts a liberation unlocked (`WorldProgress::fronts_opened_by`) and the nodes whose milestone was just reached (`Campaign::milestone_opened_nodes`). The loot block, the liberation recruit block and the next-defender picker are inline content above the bar. Every screen names outcomes with `Outcome::label` (Victory, Defeat, Retreated). Upgrades is a separate screen and the only route to the tree: it has the camp navigation row (Journey upgrades selected), the amber Back to battle (or Choose next country, or Return to active defense) and Back to camp, then the complete connected progression graph. Back to camp opens Camp home, the camp's default tab: the next defense and its defender picker, the defender roster, alerts, expeditions, offers and recent reports, with the world clock in its footer. The retired Skills and Fortifications tabs redirect there, and Fortifications frames its branch. Escape on Upgrades goes back to Results while the journey runs, else to Camp home: a liberation or Leave journey closes the journey and leaves no debrief to return to. Parallel workers retain their own orchestration and do not force the main screen to change.

`Game::continue_journey` rejects workers and unfinished main attempts. A victory continues the country's next completed frontier; defeat/withdrawal retries the reported stage. Either way it deploys `Game::next_defender` ("Choosing who defends" below). A fully liberated country returns `CountryLiberated`; the map opens with "<Country> liberated · N new fronts" and the easiest opened front preselected. Failed deployment restores the prior world selection. Continue performs no purchase or automatic training and starts a legal new round live.

`leave_journey` withdraws an active round if necessary, clears the journey-active marker/repeat plan and pauses. The application returns to menu only after its durable save acknowledgment. Leaving retains earned progression and is not a prestige reset. `journey_revision` migrates older main attempts/results into the explicit journey state.

## Choosing who defends

The next defense has one defender: you, Mara once Meet Mara is owned, or a recruit once Survivor network is owned. Results (between defenses of a running journey), the Briefing and Camp home's Next defense card carry the defender picker, and Camp home's Defenders list has "Defend next" on each row. Each dispatches `Command::SetNextDefender`, which only stores the choice in `Campaign.next_defender` and is refused while a defense is live; a defender core refuses (locked, guarding, away on an expedition, already defending, or carrying an item another deployment holds) is shown disabled with core's `DefenderBlocker` text. Until the player chooses, `Game::next_defender` is the defender of the last report, so a journey keeps its defender from one round to the next.

The Briefing primary reads "Deploy personally" or "Deploy <name>" and dispatches `Command::BeginDefense { stage }`, which deploys the next defender on the planned stage of the active country, unpauses and clears the choice. Results' continuation (`ContinueJourney`) and Upgrades' Back to battle deploy the next defender the same way; retry and repeat keep the report's defender. `Command::Deploy { stage, mode }` keeps its recorded meaning (Personal is you, Npc is Mara) for recordings and never touches the choice. A defender who cannot defend now is refused with a typed `DefenderUnavailable` and nothing changes.

When a recruit defends, it takes over the main run (STRATEGY.md, "Recruit takeover"): the HUD names it (its first name in capitals) with its own portrait, the battlefield draws its appearance, and the battle's Tactics popup edits its tactics through `SetRecruitTactics`. Camp home's "Next defense" reads "Active defense · <country> · Defense N · <name>", and its roster shows the recruit as Defending, so Operations cannot send, guard, train or equip it until the defense ends. Results and History name the recruit. Its victory pays you the completion XP as any victory does and credits the recruit, not Mara; whatever the outcome, the recruit returns to camp Ready with its items free. Sending the chosen recruit on an expedition, an operation or a guard duty hands the next defense back to you with the note "<name> left the next defense; you will defend next."

Expedition outcomes reach the main screen as toasts, one per settled expedition, acknowledged in the frame they are shown (STRATEGY.md, "Expedition outcomes"); they wait while a main defense is live and unpaused.

## Choosing a country

The journey's first country is chosen on the world map with "Start journey" (`Command::ChooseStart`): it deploys the first Personal defense paused, waiting for Begin defense. Every later country is only chosen: the World footer's "Plan defense" (or "Manage country" once liberated) dispatches `Command::SelectCountry(id)`, which makes it the active country without deploying and without spending an attempt id. It is refused, in this order, during a live defense (`DefenseInProgress`), before a starting country exists (`StartNotChosen`) and for a country that cannot be entered (`CountryLocked`, unknown ids too), and answers `CountryLiberated` for a liberated country, otherwise `Applied`. The Briefing then opens on the country's next stage, and the defense starts only with `BeginDefense`. `EnterCountry` keeps its recorded meaning (select and deploy you, unpaused) for recordings; the frontend no longer sends it.

An active outbreak is answered the same way. "Plan response" on Camp home's alerts and in Operations' Urgent outbreaks dispatches `SelectCountry`, the Briefing opens on the outbreak's final stage (`Game::outbreak_plan(country).stage`), and `BeginDefense` starts the defense; its victory contains the outbreak through the ordinary settlement. `outbreak_plan` also reports the time left, the infected groups, the guards with the garrison capacity, the recruits `AssignGuard` would accept and the recommended defender (STRATEGY.md, "Defender power and service records"). `Game::country_choice_preview(country)` gives the country dossier its stage count, its regional checkpoints and whether liberating it is what brings Mara to camp. These reads are pure and nothing about them is saved.

## One connected personal tree

The current authored `skills.json` contains 177 nodes in one connected DAG rooted at stable `pistol_training` (displayed as Survivor foundations). The seven branch labels—Foundations, Body development, Firearms, Survival, Ordnance, Fortification, Companions and world—are camera-focus/navigation chips with owned/total counts, not separate filtered trees. All 32 prior node IDs remain available.

Selection/focus only inspects. `can_purchase_node` checks preparation/reservations, ownership, every prerequisite, `minimum_victories`, `minimum_liberated` and payment. `node_payment` returns Coins or eligible LegacyBodyPoints; `purchase_node` preflights before consuming either. Prices, requirements and errors come from that same kernel.

BodyDevelopment carries attribute plus target rank, taking the highest owned rank rather than stacking duplicate ranks. The shipped tree has twenty ranks for each of five personal attributes. Blueprint and StructureRank effects integrate traps/walls/turrets and ten authored ranks per type. FeatureUnlock gates construction, companion access, recruitment, parallel deployments and operations together with their authored victory/liberation requirements.

Fresh profiles use `legacy_features=false`: XP still develops character level and future geometry, but does not mint new personal CP. Personal body development is purchased in this graph. Older missing flags use legacy compatibility: allocated body ranks count as ownership floors, existing eligible CP can pay pure BodyDevelopment nodes within the old body cap, and `legacy_graph_points` records consumed legacy points. Legacy level/point accounting remains conserved; coin-trained nodes are not a CP refund source.

A legacy allocation refund is rejected atomically if clearing those numeric floors would orphan any explicitly learned node prerequisite. Coins, points, ranks and the spent-point ledger remain unchanged on rejection; unrelated supported legacy refunds retain their old behavior. No missing ancestors are granted for free.

Mara/recruit attribute and skill advancement remains its own pinned NPC budget/ledger, not personal-tree body development. Shared engineering may improve structures in either mode; learning a firearm class still requires buying/looting and explicitly equipping an eligible owned gun.

## Authoring and compatibility

Node IDs are stable lowercase ASCII/digit/underscore strings, never saved graph indices. The catalog supports 1–256 nodes, finite globally unique positions within ±10000, up to sixteen prerequisites/effects, and one free prerequisite-free `pistol_training` root with its exact innate Pistol training effect. Every node must be reachable without a cycle. Milestone fields default to zero for old content. Existing price/name/description/effect bounds still apply; see [SKILLS_AND_WEAPONS.md](SKILLS_AND_WEAPONS.md).

New effect encodings are `BodyDevelopment{attribute,rank}`, `Blueprint(kind)`, `StructureRank{kind,rank}` and `FeatureUnlock(CampaignFeature)`. Runtime ownership adapters for old skill/body/blueprint/rank fields preserve earned state. Do not rename or silently remove learned IDs to rearrange the graph. Branch focus changes the camera, not the purchase rules or model.

[CHARACTER_COMPONENTS.md](CHARACTER_COMPONENTS.md) covers equipped appearance. [PROGRESSION_SCALING.md](PROGRESSION_SCALING.md) and [BALANCE_AND_RUN_STATS.md](BALANCE_AND_RUN_STATS.md) retain the independent level/arena/threat/balance/DPS/history contracts.

## Durable storage interface

Runtime.durable_transition_pending covers queued/in-flight critical saves and reset work, not just a visible spinner. A queued ordered SetPaused → Save boundary rejects later model commands; raw Settings edits/rebinding also freeze until the matching acknowledgment. Older autosave completion cannot clear a newer user busy state.

runner/persistence.rs owns one filesystem worker, one in-flight job and one latest coalesced pending snapshot, retaining required intents. Game/settings snapshots are owned immutable copies; no live Game mutex or widget IO crosses threads. Encoding/checksum/validation/atomic writes and recovery/archives run there. Main-frame work is snapshot capture/enqueue/poll; startup, explicit report artifacts, asset loading and shutdown are separate boundaries.

NewJourney increments a profile epoch and serializes old-save completion, full archive and fresh commit before live replacement. Old-epoch Quit success cannot navigate/exit the new profile. Quit requested during reset is recaptured against the resulting paused current generation after the reset acknowledgment. Nothing fallible follows the fresh generation's commit before reset success is reported.

PersistenceMetrics and Runtime.persistence_metrics expose pending work and completed/failed background saves/write timing. Measurements and user-stutter conclusions are separate in VALIDATION.md; moving IO is not by itself a universal FPS claim.

The complete graph keeps one-row node names visible with separate payment/state captions and full hover text. Path focus names the selected branch but never filters away other branches.

Tree presentation reads only core view helpers in `horde_core::campaign::tree_view`: `node_state` (Owned, Buyable, NeedsCoins, NeedsPrerequisites, NeedsMilestone, Unavailable) styles each node and the detail chip; `node_requirements` is the ✓/✗ checklist; `path_to_node` gives the unowned chain, total coins and first blocking milestone that the canvas highlights; `node_stat_preview` is the before→after "What changes" table; `recommended_node` is the default selection (never the owned root): the cheapest buyable node that acts now (`node_helps_now`: not a weapon class without its gun, construction without a learnable blueprint, or structure upgrades without a blueprint), body ranks after those; `search_nodes` and `upgrade_goals` back the search box and the "Path to…" menu; `legacy_node_note` explains body-rank floors only to legacy profiles. The canvas zooms on the wheel, pans on drag, moves with arrow keys, learns with Enter and jumps to the recommendation with Home; long cross-graph edges draw as labelled stubs; a translucent minimap moves the view. Learning still goes through `Command::BuySkillNode`, plays the confirm cue and pulses the node unless reduced effects is on. At narrow widths or large scale the detail panel goes below the canvas. Compact starting-country choice reserves the map before a collapsed dossier, rather than presenting management details first. The upgrade home shows one outcome line, the wallet only in the shared header, and deduplicated retreat guidance.

## Equipped presentation boundary

Purchases and equips still use core transactions; the journey screen never grants a visual item. The deployed EquipmentVisual is immutable input to player_model::resolve_equipped_model. Battle and Character preview consume selected source packets and shared sockets; original-bind parity is distinct from current action/garment acceptance. [CHARACTER_COMPONENTS.md](CHARACTER_COMPONENTS.md) describes this boundary. Developer parity/parts/matrix/repairs routes are isolated review tasks, not additional progression routes.
